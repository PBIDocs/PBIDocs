# Direct Lake Mode

Direct Lake is a Power BI storage mode built specifically for OneLake. It reads Delta tables directly from OneLake into Power BI's query engine, aiming for Import-like query speed without a traditional import step.

```text
Import:       Source -> copied into Power BI on refresh -> fast, but stale until refresh
DirectQuery:  Source -> queried live every time -> fresh, but slower
Direct Lake:  OneLake Delta tables -> read directly, no copy step -> fast and current
```

See [DirectQuery vs. Import](/docs/modeling/storage-modes) for how the two older modes work — Direct Lake is a third option that sits alongside them, available only for OneLake-backed data.

---

## Framing and Transcoding

Direct Lake doesn't import data ahead of time. Instead, a Direct Lake refresh does **framing**: it records which version of each Delta table (which Parquet files) the model should read, without copying any column values. It usually takes seconds. Queries then only see data as of the latest framing.

```text
Delta table (Parquet files in OneLake)
        |
        | framing: read metadata, map row groups
        |
Semantic model points at a specific table version, hasn't loaded values yet
        |
        | a query touches a column
        |
That column's data is transcoded into memory on demand
```

Column data is only paged into memory the first time a query actually needs it — this is why Direct Lake can open instantly even against a very large table, while still returning fast, in-memory-speed results once columns are "warmed up."

## When Direct Lake Falls Back to DirectQuery

With Direct Lake on SQL endpoints (the original flavor, built on a Lakehouse or Warehouse SQL analytics endpoint), certain conditions make queries fall back to DirectQuery through the SQL endpoint instead of the fast in-memory path. Direct Lake on OneLake models don't fall back; the query fails instead.

```text
Direct Lake query
       |
       | can it be answered from the framed, in-memory structures?
       |
       +-- Yes -> fast, VertiPaq-speed answer
       |
       +-- No  -> falls back to querying OneLake directly (DirectQuery-like)
```

Common triggers for fallback:

- A table exceeds the capacity SKU's guardrails: too many Parquet files, row groups, or rows per table, or a model too large for the SKU's memory limit (often a sign of a fragmented table that needs `OPTIMIZE`).
- A table in the model is a SQL view rather than a Delta table.
- The SQL analytics endpoint enforces row-level or object-level security that Direct Lake has to defer to.

The model's `DirectLakeBehavior` property controls this: Automatic (fall back when needed), DirectLakeOnly (error instead), or DirectQueryOnly.

Fallback doesn't produce an error — the report still returns a result, just slower, which makes it easy to miss. Performance Analyzer in Desktop (DirectQuery timings on a Direct Lake model) or a trace in DAX Studio or SQL Server Profiler shows when it happens.

## Reframing Instead of Refresh

Direct Lake models don't need a traditional data refresh, since there's no copy to refresh — but they do need **reframing** to pick up new data written to the underlying Delta tables. By default this is automatic: the model setting **Keep your Direct Lake data up to date** is on, and the model reframes when the Delta tables change.

```text
New data written to Delta table (by a pipeline, notebook, or dataflow)
        |
        | model still shows old framing until...
        |
Reframing occurs (automatically by default, or scheduled / triggered via API)
        |
        | model now reflects the new data
```

Turn automatic updates off when a pipeline writes several related tables and you don't want reports to see them half-updated; then refresh (reframe) the model as the pipeline's last step. Until a reframe happens, the model keeps showing data as of its last framing, even though the tables have changed.

---

## Table Maintenance Matters

Because framing works against a Delta table's actual Parquet file layout, how that table is maintained directly affects Direct Lake performance.

```text
Well-maintained table:                 Fragmented table:
Few, well-sized Parquet files    vs.   Many small Parquet files
        |                                      |
Fast framing, low fallback risk        Slower framing, higher fallback risk
```

Running `OPTIMIZE` (and periodically `VACUUM`) on Delta tables from a Lakehouse notebook compacts small files into larger ones, keeping row group counts low and reducing the odds of a query falling back to DirectQuery.

---

## Limitations

- Calculated columns aren't supported on Direct Lake tables, and calculated tables can't reference them. Add the column upstream (in the Delta table), or bring that data in as an Import table alongside.
- Some DAX functions and modeling features carry restrictions similar to DirectQuery, since a fallback effectively behaves like DirectQuery against OneLake.
- Row-level security is supported, but adds overhead worth testing specifically, since it changes what has to be evaluated per query rather than answered straight from the framed structures.

---

## Best Practices

- Run `OPTIMIZE` regularly on Delta tables feeding a Direct Lake model, to keep row group counts low.
- Leave automatic updates on for simple cases; when a pipeline updates several tables together, turn them off and reframe as the pipeline's final step.
- Check for fallback to DirectQuery with Performance Analyzer or a trace, rather than assuming Direct Lake speed is guaranteed.
- Reserve calculated columns and calculated tables for cases that genuinely need them, since they push a table (or column) out of pure Direct Lake behavior.

---

## Common Mistakes

### Assuming Direct Lake Always Performs Like Import

Direct Lake is fast when the underlying tables are well-maintained, but a fragmented or poorly-optimized Delta table can silently fall back to DirectQuery-level performance with no obvious error.

### Turning Off Automatic Updates and Forgetting to Reframe

With **Keep your Direct Lake data up to date** turned off, a pipeline that loads new data doesn't change what the model shows until something reframes it. Power BI also suspends automatic updates after a refresh fails with a non-recoverable error, until an on-demand refresh succeeds. If a report looks stale, check that setting and the refresh history.

### Skipping Delta Table Maintenance

Treating Delta tables as "write once and forget" lets small file fragmentation build up over time, gradually degrading Direct Lake performance until it's investigated.

---

## Direct Lake Checklist

- Underlying Delta tables are regularly optimized (`OPTIMIZE`, periodic `VACUUM`).
- Reframing is either automatic, or runs as the last step of the pipeline that updates the source tables.
- Fallback to DirectQuery is monitored, not assumed away.
- Calculated columns/tables are used deliberately, with their effect on Direct Lake behavior understood.
