The message usually reads like this, with your table names:

```text
You can't create a direct active relationship between Sales and Region because an
active set of indirect relationships already exists between these tables.
```

Power BI won't allow two different **active** routes between the same pair of tables. "Indirect relationships" means the tables are already connected **through other tables**:

```text
Sales  ──active──>  Store  ──active──>  Region      (existing route, via Store)
Sales  ──active──────────────────────>  Region      (new direct route: refused)
```

A filter on `Region` can already reach `Sales` by going through `Store`. A direct relationship would give it a second way, and if a store's region and a sale's region ever disagree, the two routes give different answers. Power BI refuses to create that ambiguity, so it lets you create the relationship only as **inactive**.

---

## Find the Existing Route

Open **Model view** and trace from one table to the other along **solid** lines (active relationships). Look for:

- **A chain through a third table**, as above: Sales → Store → Region.
- **A relationship with Both cross-filter direction.** Filters flowing both ways open routes that wouldn't exist otherwise. A bidirectional relationship between Sales and Customer can, for example, let a filter on Customer reach Region through Sales.
- **A many-to-many relationship**, which often has its direction set to Both.

---

## Fix 1: Keep the Existing Route, Use the New One on Demand

If the existing route is the one most measures should use, create the new relationship as **inactive** and switch to it only in the measures that need it:

```dax lineNumbers
Sales by Customer Region =
CALCULATE ( [Total Sales], USERELATIONSHIP ( Sales[CustomerRegion], Region[Region] ) )
```

`USERELATIONSHIP` activates the inactive relationship for that one calculation, and the model stays unambiguous everywhere else. See [USERELATIONSHIP](/docs/dax/userelationship).

## Fix 2: Set the Cross-Filter Direction to Single

If the extra route only exists because a relationship filters in **Both** directions, change it to **Single** (from the one side to the many side). Most models need very few bidirectional relationships; see [Relationships](/docs/modeling/relationships) and [CROSSFILTER](/docs/dax/crossfilter) for turning on both directions inside one measure instead.

## Fix 3: Two Different Meanings, Two Tables

Sometimes the routes mean genuinely different things: the **store's** region and the **customer's** region. Then it's two dimensions, not one. Load the region table twice (*Store Region* and *Customer Region*), relate each to the right column, and both relationships can be active, because they connect different tables.

---

## The Same Two Tables Twice: Dates

A related situation doesn't raise this error at all. When a fact table has two date columns, `OrderDate` and `ShipDate`, and you relate both to the same `Date` table, Power BI creates the second relationship as **inactive** automatically. Only one relationship between the same two tables can be active.

You have the same choices:

- **One date is primary** (most measures use `OrderDate`): keep `ShipDate` inactive and use `USERELATIONSHIP` in the few ship-date measures.
- **Both must be sliced independently**, with an order-date slicer and a ship-date slicer at the same time: add a second date table (`Ship Date`) with its own active relationship. This is a *role-playing dimension*. See [Date Tables](/docs/modeling/date-tables#multiple-date-relationships).

## Common Mistakes

**Deleting the other relationship to make the error go away.** Check which measures and visuals rely on the existing route first.

**Turning every relationship to Both.** It's the most common way to create unexpected routes, and ambiguity, in the first place.

**Using USERELATIONSHIP when independent slicers are needed.** It changes the relationship inside one measure; it doesn't make a slicer filter through the inactive relationship. That needs a second table.
